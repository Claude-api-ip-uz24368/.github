<h2>一、实验怎么设计：只改一个变量</h2>
<h3>对照组与实验组的划分</h3>
<p>十二个号分成两组，每组六个号，尽量让两组在号龄、注册地区、日均调用量上接近。A 组走机房出口，B 组走原生家宽出口。除了出口之外，其他条件全部保持一致：同一套客户端版本、同一个请求脚本、同一时段执行、同一个人操作。这样出的差异才能归因到出口上。</p>
<h3>观测指标只有四个</h3>
<p>成功率、P95 延迟、验证码或二次验证出现次数、单次任务中断次数。四个指标都能量化，不需要主观打分。记录方式建议用一个 CSV，每次请求追加一行，字段包括时间、组别、出口 IP、返回码、耗时。三周下来大约几千行，用表格软件透视一下就出结论。</p>

<h2>二、第一轮：注册环节的通过情况</h2>
<p>这一轮只做注册，不调用业务接口。六个号分两天注册完，每天三个，注册后立刻记录是否被要求额外验证。这一步的差异通常最明显，也最容易被误读成「出口决定一切」。</p>
<h3>观察到的现象</h3>
<p>A 组六个号里有四个走完了全流程，两个在提交后要求二次验证；B 组六个号里五个一次通过，一个因为填写的地区与出口城市不一致被拦。注意最后那一个：被拦的原因不是出口属性，而是信息不自洽。这说明出口是必要条件之一，不是充分条件。</p>

<h3>怎么排除偶然</h3>
<p>六个号的样本太小，一次结果说明不了太多。建议把这一轮重复两批，看趋势是否一致。如果两批的差异都在两成以上，可以认为有效；如果一批通过率高一批低，那就是随机波动，别急着下结论。</p>

<h2>三、第二轮：连续七天登录的一致性</h2>
<h3>看的是波动，不是平均值</h3>
<p>很多评测只报平均成功率，这个指标容易掩盖问题。真正影响体验的是波动：A 组每天的成功率在百分之八十五到九十八之间来回跳，B 组稳定在百分之九十七到九十九。平均值可能只差几个点，但 A 组那种忽高忽低的体验会让自动化任务频繁重试。</p>
<h3>中断恢复的时间差</h3>
<p>记录每次中断到恢复的间隔。A 组的中位恢复时间是四分钟，最长一次接近半小时；B 组中位一分半。这个差距在长任务里被放大：一个跑四十分钟的批处理，A 组有两次因为中断从头再来，B 组只重试了一次。</p>

<h2>四、第三轮：并发调用下的表现差异</h2>
<h3>把并发推到实际峰值的一点五倍</h3>
<p>两组同时开三个并发，持续十分钟。A 组在第两分钟开始出现连续失败，返回码以超时和限流为主；B 组全程没有连续失败，但有两次单请求超时。差别在于出口侧的排队策略：机房段通常是多人共享上行，你的请求要和同段其他客户抢带宽。</p>
<h3>一个容易忽略的变量</h3>
<p>并发测试的结果和你自己的客户端实现强相关。如果脚本没有指数退避，失败会雪崩；加了退避，同样的出口表现会好很多。所以看到别人说「某出口扛不住并发」，先问一句他的重试逻辑怎么写的。</p>

<h2>五、实验能说明什么，不能说明什么</h2>
<h3>能说明的</h3>
<p>在同等条件下，出口属性会明显影响请求的稳定性和中断后的恢复速度，这个结论在你的业务里成立。它还说明了信息自洽比出口类型更基础：一个出口再好，资料和时区对不上也会被拦。</p>
<h3>不能说明的</h3>
<p>不能说明住宅出口可以解决所有问题。账号历史、请求频率、客户端实现、支付方式都在起作用，其中任何一项出问题，换出口都不会有改善。也不能用这组数据推断别的地区、别的供应商的表现，地域差异很大。</p>
<h3>落地建议</h3>
<p>按实验结论，把号分成两组：核心号走住宅出口并固定城市，边缘号留在机房出口做低频任务。下单后当天把环境配好，配完先跑一周观测，不对就换，别拖。选供应商时把响应时限写进单子，出了问题直接找对接的人，跟到能跑通为止，这比任何参数都实在。</p>

<h2>常见问答</h2>
<h3>至少要多少个号才能做出可信的对照？</h3>
<p>答：每组六个是下限，能到每组十个更稳。样本少于五个时，单个号的偶然因素会盖过出口差异。</p>
<h3>实验期间能不能换客户端版本？</h3>
<p>答：不能。版本变化会改变请求头和超时策略，等于引入了第二个变量。整个实验期锁定版本，结束后再升级。</p>
<h3>住宅出口的延迟更高怎么办？</h3>
<p>答：会高一些，通常多几十毫秒。判断标准不是绝对值，而是 P95 是否稳定。稳定在可接受范围内就没问题，忽高忽低才需要处理。</p>
<h3>这套实验能用在其他模型接口上吗？</h3>
<p>答：可以，方法通用。但不同服务的风控策略和限流阈值不同，结论要各自验证，不能直接套用。</p>
